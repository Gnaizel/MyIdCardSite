# Выкладка на сервер

Сайт поднимается тремя контейнерами: `caddy` → `my-site` → `visitor-db`.

```
интернет ──80──► caddy ──308 redirect──► https
          ──443─► caddy ──http:8080──► my-site ──► visitor-db
```

Наружу торчит только Caddy. Он же сам получает сертификат Let's Encrypt,
сам его продлевает и сам уводит весь http на https. Ни certbot, ни cron,
ни ручного обновления сертификатов не нужно.

Приложение внутри остаётся на обычном http — так и должно быть: TLS
заканчивается на Caddy.

---

## Что нужно один раз

### 1. DNS

A-запись домена должна указывать на IP сервера:

| Тип | Имя | Значение |
|---|---|---|
| A | `@` | IP сервера |
| A | `www` | IP сервера |

Проверить, что запись разъехалась:

```bash
dig +short gna1zel.online
```

Пока здесь не появится IP сервера — сертификат не выдадут. Обычно это
минуты, но у некоторых регистраторов до пары часов.

Если `www` заводить не хочешь — не заводи, но тогда удали из `Caddyfile`
последний блок `www.{$SITE_DOMAIN}`, иначе Caddy будет бесконечно
пытаться получить сертификат, которого не выдадут.

### 2. Сервер: docker и firewall

```bash
# docker + compose plugin
curl -fsSL https://get.docker.com | sh

# порты наружу: ssh, http, https
# 22 разрешаем ДО enable, иначе ufw отрежет собственную ssh-сессию
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
# 443/udp — это HTTP/3, без него сайт работает, просто по HTTP/2
ufw allow 443/udp
ufw --force enable
```

> Важно понимать: docker правит iptables в обход ufw, поэтому опубликованный
> контейнером порт будет открыт наружу, даже если ufw его «запрещает».
> Именно поэтому база и приложение в `docker-compose.yaml` привязаны к
> `127.0.0.1` — вот это docker соблюдает, и снаружи до них не достучаться.
> Не убирай `127.0.0.1:` из `ports`, иначе postgres уедет в интернет.

**80 нужен обязательно**, даже при том что сайт работает по 443: по нему
Let's Encrypt проверяет, что домен действительно твой (ACME HTTP-01).
Закроешь 80 — сертификат не выпустится и не продлится.

Проверить, что порты свободны:

```bash
ss -tlnp | grep -E ':(80|443)\s'
```

Если там уже висит apache/nginx — снести или остановить, иначе Caddy
не стартует.

### 3. Код и ключи

```bash
git clone <репозиторий> /opt/mysite
cd /opt/mysite
cp .env.example .env
nano .env
```

В `.env` обязательно заполнить:

| Переменная | Значение |
|---|---|
| `SITE_DOMAIN` | `gna1zel.online` — без `https://` и без слеша |
| `ACME_EMAIL` | своя почта — на неё Let's Encrypt напишет, если продление сломается. Можно оставить пустой |
| `POSTGRES_PASSWORD` | длинная случайная строка: `openssl rand -base64 24` |

Остальные ключи (last.fm, steam, github, гостевая книга) — как в
[README-LOCAL.md](README-LOCAL.md). Без них сайт работает, просто
соответствующие блоки напишут, что данных нет.

> `POSTGRES_PASSWORD` читается postgres **только при первом создании базы**.
> Если поменять его потом, том останется со старым паролем и приложение
> не достучится. Менять позже — через `ALTER USER postgres PASSWORD '...';`
> и синхронно в `.env`.

### 4. Запуск

```bash
docker compose up -d --build
```

Сборка идёт внутри образа: JDK и maven на сервере не нужны, `mvn package`
заранее делать не надо. Первый раз это несколько минут — качаются
зависимости.

### 5. Проверка

```bash
# http должен отдать 308 на https
curl -sI http://gna1zel.online | head -3

# https должен отдать 200 и валидный сертификат
curl -sI https://gna1zel.online | head -3

# кто выдал сертификат и до какого числа
echo | openssl s_client -connect gna1zel.online:443 -servername gna1zel.online 2>/dev/null \
  | openssl x509 -noout -issuer -dates
```

Ожидаемо: `308 Permanent Redirect` на первом, `200 OK` на втором,
`issuer=...Let's Encrypt...` на третьем.

Логи, если что-то пошло не так:

```bash
docker compose logs -f caddy      # выпуск сертификата виден здесь
docker compose logs -f my-site
```

## Обновление сайта

```bash
cd /opt/mysite
git pull
docker compose up -d --build
```

Сертификаты и база переживают пересборку: они в томах `caddy-data`
и `visitor-db-data`.

## Сертификаты

Лежат в томе `caddy-data`. Caddy продлевает их сам примерно за 30 дней
до конца — ничего настраивать не нужно, сервис просто должен быть запущен.

Том `caddy-data` не удалять: вместе с сертификатами там ключ аккаунта
Let's Encrypt. Потеряешь — всё выпускается заново, а у Let's Encrypt есть
лимит: 5 выпусков на домен в неделю. Поэтому и `docker compose down -v`
на проде лучше не делать никогда.

Бэкап на всякий случай:

```bash
docker run --rm -v mysite_caddy-data:/data -v $(pwd):/backup alpine \
  tar czf /backup/caddy-data.tar.gz -C /data .
```

## Если что-то не так

**Сертификат не выдаётся.** Смотреть `docker compose logs caddy`.
Почти всегда одно из трёх: A-запись ещё не разъехалась, порт 80 закрыт
фаерволом, или на 80 уже что-то висит.

**`too many certificates already issued`** — упёрся в лимит Let's Encrypt
после нескольких неудачных попыток. Лимит недельный, ждать. Чтобы не
попадать в него при отладке, можно временно переключиться на тестовый
центр: добавить в глобальный блок `Caddyfile`

```
acme_ca https://acme-staging-v02.api.letsencrypt.org/directory
```

Сертификат будет невалидным для браузера, но проверит, что вся схема
рабочая. После отладки строку убрать и один раз сделать
`docker compose restart caddy`.

**Сайт открывается, но в гостевой книге у всех один IP** — значит до
приложения не доходит `X-Forwarded-For`. Проверить, что в
`docker-compose.yaml` у `my-site` стоит `TRUST_FORWARDED_FOR=true`.
Сам заголовок проставляет Caddy, настраивать его не нужно; сломать это
может только глобальный `trusted_proxies` в `Caddyfile` — тогда Caddy
начнёт верить заголовку клиента, и адрес станет можно подделать.

**Браузер держит http и не пускает на https** — это HSTS с прошлого раза.
Сбрасывается в `chrome://net-internals/#hsts`.

## Безопасность

Что уже сделано в конфигах:

- postgres слушает только `127.0.0.1` — снаружи до базы не достучаться;
- приложение слушает только `127.0.0.1:8080` — в обход https на него
  не зайти;
- `/actuator` закрыт на прокси;
- `X-Forwarded-For` перезаписывается прокси, подделать адрес нельзя;
- HSTS на год: браузер после первого визита сам не пойдёт по http.

Что стоит сделать руками на сервере:

```bash
# зайти по ключу вместо пароля
ssh-copy-id root@<IP сервера>

# после проверки, что ключ работает — выключить вход по паролю
sed -i 's/^#*PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl restart ssh
```

Пароль root, если он где-то засветился (в чате, в переписке, в истории
команд), сменить: `passwd`.
